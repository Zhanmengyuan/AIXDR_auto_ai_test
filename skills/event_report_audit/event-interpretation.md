# 事件解读报告

## 核心原则

1. **零前置输出**：报告内容必须从 `# 事件解读报告` 开始，前面严禁出现任何解释性、过渡性、思考性文字（如"现在我有了完整的事件信息，我来生成报告"、"基于以上数据，输出如下"等）。严禁输出报告内容以外的任何字符。
2. **统一输出6章**：第1→2→3→4→5→6，顺序不变，少一章算失败。
3. **第1章必须讲清楚"事件做了什么"**：用一句白话概括"攻击者通过什么手段、做了什么动作、可能造成什么后果"，这是事件解读区别于告警解读的核心价值。
4. **聚合视角先行**：事件 = 多告警聚合（也可能=1条），所有实体（攻击者/受害者/载荷）必须先去重聚合再展示，不准把同一个源IP分多条列。
5. **第4/5/6章看威胁定性和攻击结果两个维度**：
   - 威胁定性=不能确认 → 第4/5/6章均只输出指定文案（最高优先级）
   - 威胁定性=误报 → 第4章输出"事件经研判为误报，无实际攻击影响。"第5章输出"事件经研判为误报，无后续攻击风险。"第6章输出误报确认与规则优化建议
   - 威胁定性=正报 且 攻击结果=成功 → 第4/5章填详细内容，第6章填处置建议
   - 威胁定性=正报 且 攻击结果=失败/未知 → 第4/5章只输出指定文案，第6章填排查建议
6. **第6章看威胁定性和攻击结果两个维度**：不能确认→固定文案；误报→误报确认+规则优化；正报+成功→处置建议；正报+失败/未知→排查建议。四套不准混填。
7. **两个维度严禁混淆**：第1章写"正报/误报/不能确认"，第3章写"成功/失败/未知"。
8. **零字段名**：全文不准出现 RESULT、ALERT_RESULT_FLAG、event_info、asset_info 等任何英文字段名。
9. **严禁捏造**：缺失证据只准写证据类型名称，不准编造具体路径、命令示例、IP地址。
10. **建议分层可操作**：处置/排查建议必须按"按攻击者维度→按资产维度→按载荷维度"分维度组织 + "快速验证→范围排查→深层取证"分层组织，必须给出可执行命令。
11. **威胁定性（第1章）与攻击结果（第3章）是两个完全独立的维度，不存在任何推导关系。**

## 数据获取流程

**第一步**：调用 `base_extractInfoForInterpret(bizType=2, bizId=事件ID)` 获取事件抽取信息，返回 `event_info`（事件核心信息）、`asset_info`（受影响资产数组）、`intelligence_info`（关联情报）、`vuln_info`（关联脆弱性）。

**第二步**：仅当威胁定性=正报且攻击结果=成功时，对关联告警中攻击结果为成功的告警调用 `alarm_getAlarmById(snowId=告警ID)` 补充举证细节，调用数量不超过3条。其他情况（误报/不能确认/攻击失败/攻击未知）禁止调用此接口，避免数据膨胀。

**第三步**：若 `asset_info` / `AFFECTED_ASSET_INFO` 存在，需调用 `asset_pageAsset` + `asset_fingerprintPage` 获取每台受影响资产的详情和指纹（运行服务、中间件、数据库、开放端口、操作系统、责任人）。

**所有数据获取完成后**再开始输出报告，严禁边调工具边输出章节。

```
# 事件解读报告
> **事件编号：** [SNOW_ID]
> **事件名称：** [ALERT_NAME]
> **生成时间：** [YYYY-MM-DD HH:MM]
> **关联告警数：** [N 条]   **时间跨度：** [START_TIME ~ END_TIME]
---
**一句话总结：** [一句白话总结，必须包含"攻击者+动作+对象+后果"四要素。例如："攻击者从XX国家1个外网IP对内网3台Web服务器发起SQL注入扫描，其中1台命中并疑似获得数据库读取权限。"]
---
```

**铁律**：白话总结严禁出现"检测到N条告警"这种废话，必须直接讲清楚业务语义（谁干了什么、打了谁、有没有打中）。

## 场景化字段关注指引

事件字段与告警字段大量重叠。事件特有字段集中在"聚合"维度（关联告警数、聚合规则、时间跨度、是否多攻击源/多受害资产），其他字段沿用告警语义。

### 威胁定性相关
- 读取 `ALERT_RESULT_FLAG`，值为1→正报，2→误报，3或空→不能确认。**严禁自己判定**
- 事件定性来自聚合后的引擎/AI研判结论，**不准用"该事件下大部分告警是正报"自行推断事件定性**，引擎说什么就是什么。

### 攻击结果相关（事件维度）
- 读取 `RESULT`，取结论即可。
- **`RESULT`字段为空时，攻击结果必须为"未知"，严禁AI基于关联告警列表自行推断事件整体成功或失败**。
- **事件攻击结果与单告警结果可能不一致**：事件下5条告警，3条成功2条失败 → 事件攻击结果一定是以引擎给出的攻击结果为准；

### 事件聚合维度（事件特有，必须关注）
- 关联告警数量（来自 event_info 的告警列表长度或聚合计数字段）
- 时间跨度：`START_TIME` ~ `END_TIME` 或首末告警时间，反映持续时长（瞬时爆发 vs 长期渗透）
- 检测引擎分布：关联告警中网络/终端引擎各占多少
- 聚合维度：按攻击者聚合（同源IP多目标）/按受害者聚合（同目标多攻击者）/按载荷聚合（同样本多次出现）
- 攻击链阶段分布：关联告警的 `KILL_CHAIN` 是否覆盖多个阶段（侦察→投递→利用→C2→行动）

### 事件涉及网络实体（聚合后）
- 源IP集合：聚合去重的 `ATTACKER_IP` 列表，标注每个IP的出现频次、源属地
- 目的IP集合：聚合去重的 `VICTIM_IP` 列表，标注每个IP的出现频次、目的属地
- 流量方向分布：`DIRECTION` 各方向占比
- 域名/URL集合：聚合去重的 `HTTP_REQ_HOST`、关联IOC

### 受影响资产（平台识别，聚合）
**判定规则（优先级）**：
1. **优先从 `AFFECTED_ASSET_INFO` / `asset_info` 读取**（平台已识别的受影响资产列表）。**服务器资产优先展示在前**，办公终端排后。
2. **`AFFECTED_ASSET_INFO` / `asset_info` 为空时**，结合各关联告警的 `DIRECTION` 从 `ATTACKER_IP`/`VICTIM_IP` 推断：
   - `外对内` → 受影响资产IP = `VICTIM_IP`
   - `内对外` → 受影响资产IP = `ATTACKER_IP`
   - `内对内` → 受影响资产IP = `VICTIM_IP`（通常）
   - 方向缺失 → 标注"攻击方向未明确，无法确定受影响资产IP"
3. **资产去重聚合**：同一资产被多条告警命中，只展示1次，但需统计"该资产关联N条告警"。
4. **资产详情**：调用 `asset_pageAsset` + `asset_fingerprintPage` 获取，未调用或未返回写"—"。

### 攻击载荷（聚合视角，按检测类型关注）

**事件载荷与告警载荷字段一致，但需做"族谱聚合"**：同名/同Hash文件、同域名C2、同CVE漏洞利用，归为一类后展示出现次数。

- **网络检测类**：`PROTOCOL`、`HTTP_METHOD`、`HTTP_REQ_HOST`、`HTTP_REQ_URI`、`HTTP_RESP_CODE`、`HTTP_REQ_BODY`/`HTTP_RESP_BODY`、`PAYLOAD2S`/`PAYLOAD2C`
- **终端检测类**：`MAIN_PROCESS_NAME`、`MAIN_PROCESS_PATH`、`MAIN_PROCESS_USER`、`TARGET_PROCESS_PATH`、`TARGET_PROCESS_CMD`、`FILE_PATH`/`FILE_NAME`、`FILE_CHECKSUM`、`VIRUS_NAME`/`VIRUS_TYPE`/`VIRUS_CLASS`、`TREE_EDGES`/`TREE_NODES`
- **邮件检测类**：`MAIL_SENDER`、`MAIL_RECIPIENT`、`MAIL_CC`、`MAIL_SUBJECT`、`MAIL_MSG`
- **挖矿/外联类**：`MINING_POOL`、`MINING_STAGE`、外联IP/端口
- **登录异常类**：`LOGIN_USER`、`LOGIN_PATH`、`START_TIME`/`END_TIME`、来源IP、`LOGIN_PWD`
- **漏洞利用类**：`CVE`/`CNNVD`、`AFFECTED_OS`、漏洞特征载荷

### 情报关联相关（聚合）
- 读取 `intelligence_info` 中的情报命中统计：命中N条 / 未命中M条
- 高置信度情报标签（`MALDIUM_THREAT`、`MALDIUM_CONFIDENCE`、`MALDIUM_SEVERITY`）需在第2章单独突出
- 关联历史攻击事件（同源IP/同载荷历史命中）

### 处置状态相关（事件维度）
- 读取事件 `HANDLE_STATUS`（-1未处置、0处置中、1已处置）、`HANDLE_RESULT`
- 各关联告警的处置状态分布：已处置X条/未处置Y条

## 强约束判定规则

### 威胁定性判定

**读取字段**：`ALERT_RESULT_FLAG`
- 值为1 → 正报
- 值为2 → 误报
- 值为3或空 → 不能确认

**输出表述要求**：判定依据中严禁引用具体字段名说明缺失原因。
- 正确示例："信息不充分，无法完成事件定性"
- 错误示例："引擎未返回明确的正报/误报标识"（暗示AI解读无价值，严禁出现）
- 错误示例："ALERT_RESULT_FLAG为空"（暴露字段名，严禁出现）

### 攻击结果判定

直接读取字段： `RESULT`（引擎检测结果，严禁AI基于关联告警或者事件信息自行推断攻击结果）

- **引擎已判定的事件攻击结果不准被AI推翻**：禁止以"虽然引擎说成功但缺乏佐证"为由改写为未知。

**输出表述要求**：攻击结果表述统一为"经综合研判"，严禁说明判定依据或字段来源。

### 分支规则（决定第4/5/6章填什么）

- 第1章威胁定性写"不能确认" → 第4/5/6章均只输出指定文案（最高优先级，覆盖下面所有规则）
- 第1章威胁定性写"误报" → 第4/5/6章均只输出误报专用文案
- 第3章攻击结果写"成功" 且 第1章威胁定性写"正报" → 第4/5/6章填详细内容
- 第3章攻击结果写"失败"或"未知" 且 第1章威胁定性写"正报" → 第4/5章写固定提示语，第6章写排查建议

**固定提示语**：
- 第4章：当前攻击结果未确认成功，暂无法评估当前攻击影响。
- 第5章：当前攻击结果未确认成功，暂无法预测后续风险。

**误报专用文案**：
- 第4章：事件经研判为误报，无实际攻击影响。
- 第5章：事件经研判为误报，无后续攻击风险。
- 第6章：输出误报确认建议与规则优化建议（见第6章模板）

**铁律**：

## 铁律

1. **统一输出6章**：第1→2→3→4→5→6，顺序不准变，少一章算失败。
2. **第1章必须讲清楚"事件做了什么"**：白话总结必须包含攻击者+动作+对象+后果四要素，业务语义优先；严禁工具视角描述（如"该事件包含N条告警"）。
3. **聚合视角**：所有实体（攻击者/受害者/载荷）必须先去重聚合再展示，标注命中次数；严禁同一实体分多行列；严禁把多告警事件当成单告警来写。
4. **第3章必须按资产聚合呈现结果矩阵**：这是事件解读相对告警解读的核心增量。
5. **第4/5/6章看威胁定性和攻击结果两个维度**：不能确认→固定文案；误报→误报专用文案；正报+成功→详细内容/处置建议；正报+失败/未知→固定文案/排查建议。四套不准混填。
6. **误报≠攻击未成功**：误报意味着事件本身不是真实攻击，第4/5章输出"无攻击影响/无攻击风险"，第6章聚焦误报确认和规则优化，严禁把误报和"攻击失败"混为一谈。
7. **第6章必须三维分解**：按攻击者/资产/载荷三维度组织，每维度内部再按快速验证/范围排查/深层取证三层；多资产事件必须给出批量执行方式。
8. **攻击载荷单一出口**：全空写"未提取到攻击载荷信息"，不准逐行列"—"。
9. **两个维度严禁混淆**：第1章写"正报/误报/不能确认"，第3章写"成功/失败/未知"。
10. **零字段名**：全文不准出现 RESULT、ALERT_RESULT_FLAG、event_info、asset_info、intelligence_info 等任何英文字段名；判定依据中严禁引用字段名说明缺失原因。
11. **严禁推翻引擎结论**：引擎已判定成功/失败的，严禁以"证据不足""缺乏佐证"等理由修正为未知。只有全部引擎结果为空时，才允许判断为未知。
12. **严禁捏造**：缺失证据清单只准写证据类型名称，不准编造具体路径、命令示例、IP地址；批量命令中的IP/Hash列表必须基于实际数据。
13. **建议分层可操作**：排查/处置建议必须按三维度+三层组织，必须根据事件类型动态调整重点，必须给出可执行命令（含参数），禁止"进一步排查""加强监控""建议关注"等笼统描述。
14. **第4章不准矛盾**：第2章有资产的，第4章（成功时）不准写"未查询到受影响资产信息"。
15. **服务器优先原则**：第2章受害者列表、第4章影响面统计中，服务器资产必须排在办公终端之前。

# AI 智能体统一测试框架方案

> 版本：v1.0
> 日期：2026-11-17

***

## 一、背景

### 1.1 现状

目前 AIXDR 平台已有 10+ 个 AI 智能体在运行，分布在四大业务类别中：

| 类别    | 智能体                                   | 数量 |
| ----- | ------------------------------------- | -- |
| 检测研判类 | WAF降噪、恶意文件检测、钓鱼邮件检测、Webshell检测、本地情报提取 | 5  |
| 内容生成类 | 安全告警解读、安全事件解读、资产解读、漏洞解读、沙箱文件解读        | 5  |
| 查询类   | text2sql、数字人知识查询                      | 2  |
| 知识问答类 | RAG检索                                 | 1  |

各智能体的测试**分散在不同团队、不同脚本、不同格式中**，存在以下问题：

| 问题        | 表现                                      |
| --------- | --------------------------------------- |
| 测试结果不互通   | 每个智能体用自己的格式存结果，无法横向对比                   |
| 版本迭代无统一判定 | 180→190 升级时，靠人工逐个看报告判断"能不能升级"，效率低且标准不统一 |
| 新智能体接入成本高 | 没有标准接口，接入新智能体要从头写测试+报告代码                |
| 对外汇报缺整体视图 | 领导想看"这次升级整体怎么样"，没有一份覆盖所有智能体的综合报告        |

### 1.2 核心矛盾

各智能体测试方式差异巨大（SSE流式、异步轮询、SQL执行、RAG评估等），**强行统一测试执行方式不现实**。但测试**结果的汇总、评分、对比**是可以标准化的。

***

## 二、核心目标

### 2.1 本次要解决的核心问题

```
1、汇总结果；2、判定版本好坏；3、出统一报告
```

具体三个目标：

| 目标          | 说明                                 |
| ----------- | ---------------------------------- |
| **1. 统一汇总** | 各智能体跑完测试后，按统一格式输出结果，框架自动汇总         |
| **2. 版本判定** | v180→v190 能不能升级，框架自动给出结论（不是靠人工看报告） |
| **3. 统一报告** | 一份报告覆盖所有智能体，按维度横向对比，支持版本总结汇报       |

### 2.2 不做什么

| 不做        | 原因                        |
| --------- | ------------------------- |
| 不统一测试执行方式 | 各智能体测试方式差异大，不强行统一，成本高且没必要 |

***

## 三、改造方案

### 3.1 整体架构（分层设计）

整个框架采用**分层设计**，从下往上四层，每层职责独立、可单独修改：

```
┌─────────────────────────────────────────────────────────┐
│ 第四层：报告层                                            │
│ 当期报告 / 版本对比报告 / 专项报告 / 部分参测报告           │
│ 改报告样式不影响数据结构和评分逻辑                         │
├─────────────────────────────────────────────────────────┤
│ 第三层：评分层                                            │
│ 归一化 → 维度归并 → 分类加权 → 评级                       │
│ 改权重不影响归一化公式，改公式不影响数据结构                 │
├─────────────────────────────────────────────────────────┤
│ 第二层：校验层                                            │
│ 按声明文件校验JSON格式和必填字段                           │
│ 新智能体加声明文件即可，不影响已有智能体                    │
├─────────────────────────────────────────────────────────┤
│ 第一层：数据层                                            │
│ 各团队上传 StandardResult JSON                           │
│ 各团队测试脚本不动，跑完加一步输出JSON即可                  │
└─────────────────────────────────────────────────────────┘
```

**分层设计的好处**：

| 好处   | 说明                       |
| ---- | ------------------------ |
| 层间解耦 | 每层只依赖下一层的输出，不关心下层怎么实现    |
| 独立修改 | 改报告样式不影响评分逻辑，改权重不影响数据结构  |
| 独立扩展 | 加新智能体只动数据层+校验层，加新报告只动报告层 |
| 独立测试 | 每层可单独测试验证，不需要全链路跑通       |

**数据流向**：

```
各智能体现有测试脚本（不动）
    │
    │  跑完测试后，输出标准格式JSON
    │  （StandardResult 契约）
    ▼
┌─────────────────────────────────────┐
│        汇总 · 评分 · 报告层           │
│  （本次新建，轻量，不侵入现有脚本）     │
│                                     │
│  1. 扫描结果目录，读取所有JSON        │
│  2. 按维度归一化打分                 │
│  3. 逐指标版本对比 + 回归门禁检查     │
│  4. 综合分 + 评级                    │
│  5. 出统一HTML报告                   │
└─────────────────────────────────────┘
```

### 3.2 两层判定机制

版本好坏的判定分两层，各司其职：

#### 第一层：发布决策层（逐指标对比 + 回归门禁）

**这是判定"能不能升级"的核心，不算综合分。**

逐指标对比 v180 vs v190，每个指标分三档：

| 档位   | 判定条件          | 含义    |
| ---- | ------------- | ----- |
| ↑ 提升 | 变化 > 显著阈值（正向） | 真实改善  |
| → 持平 | 变化在噪声范围内      | 无实质变化 |
| ↓ 退化 | 变化 > 显著阈值（负向） | 真实退化  |

显著阈值按指标类型设定，避免统计噪声误判：

| 指标类型   | 显著阈值 | 说明                 |
| ------ | ---- | ------------------ |
| 准确率类   | 2pp  | 百分点变化 >2% 才算真实变化   |
| F1 类   | 0.02 | F1 变化 >0.02 才算真实变化 |
| 响应时间类  | 10%  | 相对变化 >10% 才算真实变化   |
| LLM评分类 | 3分   | 100分制变化 >3分 才算真实变化 |

**回归门禁**：部分核心指标设为门禁指标，退化超过门禁阈值则一票否决：

```yaml
门禁规则示例：
  - 威胁定性准确率：退化 > 5pp → 触发门禁
  - 风险等级准确率：退化 > 5pp → 触发门禁
  - 文件性质判定准确率：退化 > 3pp → 触发门禁
  - 核心结论稳定性：退化 > 10pp → 触发门禁
```

**发布决策结论**：

| 结论      | 条件                          |
| ------- | --------------------------- |
| ✅ 建议升级  | 提升指标 ≥3个 且 无门禁触发 且 退化指标 ≤2个 |
| ⚠️ 谨慎升级 | 提升指标 > 退化指标 且 无门禁触发         |
| ❌ 不建议升级 | 有门禁触发 或 退化指标 > 提升指标         |

#### 第二层：汇报展示层（综合分 + 评级）

**这是版本总结"整体水平"的，辅助参考，不作为发布决策唯一依据。**

每个指标先归一化为 0\~100 标准分，再按维度聚合，最后按分类权重加权：

```
原始指标 → 归一化(0~100) → 维度均值 → 分类权重加权 → 综合分(0~100) → 评级
```

归一化四种类型（每个原始指标先转为 0\~100 标准分）：

#### 类型1：higher\_better（越高越好）

**公式**：`标准分 = raw ÷ best × 100`

**含义**：原始值越接近 best 得分越高，等于 best 得 100 分，等于 worst 得 0 分。best 和 worst 由各智能体按业务实际设定。

**适用指标**：

| 指标                | best      | worst   | 示例                              |
| ----------------- | --------- | ------- | ------------------------------- |
| 判定准确率             | 1.0（100%） | 0.0（0%） | 97.67% → 97.67÷1.0×100 = 97.67分 |
| F1                | 1.0       | 0.0     | 0.977 → 97.7分                   |
| 威胁定性准确率           | 1.0       | 0.0     | 100% → 100分                     |
| 攻击结果准确率           | 1.0       | 0.0     | 98% → 98分                       |
| 风险等级准确率           | 1.0       | 0.0     | 100% → 100分                     |
| 格式合规率             | 1.0       | 0.0     | 98% → 98分                       |
| IOC召回率            | 1.0       | 0.0     | 100% → 100分                     |
| IOC精确率            | 1.0       | 0.0     | 99.88% → 99.88分                 |
| 忠实度 Faithfulness  | 1.0       | 0.0     | 0.767 → 76.7分                   |
| 答案正确性 Correctness | 1.0       | 0.0     | 0.840 → 84.0分                   |
| 答案相关性 Relevancy   | 1.0       | 0.0     | 0.834 → 83.4分                   |
| 上下文精确度 Precision  | 1.0       | 0.0     | 0.857 → 85.7分                   |
| 上下文召回率 Recall     | 1.0       | 0.0     | 0.734 → 73.4分                   |
| 固定答案准确率           | 1.0       | 0.0     | 93.1% → 93.1分                   |

> 说明：准确率类指标 best=1.0 worst=0.0 是最常见配置，表示 0% 得0分、100% 得满分。best 和 worst 按智能体各自设定，例如某指标业务底线是80%，也可以设 best=1.0 worst=0.8，低于80%直接0分。

#### 类型2：lower\_better（越低越好）

**公式**：`标准分 = (1 - (raw - best) / (worst - best)) × 100`

**含义**：原始值越接近 best（越小）得分越高，等于 best 得 100 分，等于 worst 得 0 分，中间线性插值。

**适用指标**：

| 指标               | best | worst | 示例                                              |
| ---------------- | ---- | ----- | ----------------------------------------------- |
| 首包响应时间（解读类）      | 0.5s | 5.0s  | 0.2s → (1-(0.2-0.5)/(5.0-0.5))×100 = 106→截断100分 |
| 首包响应时间（检测类）      | 1.0s | 8.0s  | 1.68s → (1-(1.68-1.0)/(8.0-1.0))×100 = 90.3分    |
| 平均响应时间（解读类）      | 15s  | 90s   | 21.2s → (1-(21.2-15)/(90-15))×100 = 91.7分       |
| 平均响应时间（检测类）      | 5s   | 180s  | 9.74s → (1-(9.74-5)/(180-5))×100 = 97.3分        |
| 平均响应时间（沙箱）       | 20s  | 300s  | 51.7s → (1-(51.7-20)/(300-20))×100 = 88.7分      |
| 平均响应时间（text2sql） | 5s   | 60s   | 18.6s → (1-(18.6-5)/(60-5))×100 = 75.3分         |
| P95响应时间（WAF）     | 10s  | 60s   | 17.47s → (1-(17.47-10)/(60-10))×100 = 85.1分     |

> 说明：阈值按智能体各自设定。解读类首包 best=0.5s，检测类 best=1.0s，因为检测类接口天然比解读类慢，不能用同一套阈值。得分超过100分时截断为100。

#### 类型3：pass\_fail（通过率）

**公式**：`标准分 = pass_count ÷ total × 100`

**含义**：统计通过次数占总次数的百分比，直接转为0\~100分。无需 best/worst 阈值。

**适用指标**：

| 指标                  | 计算方式                 | 示例               |
| ------------------- | -------------------- | ---------------- |
| 核心结论稳定性（告警/事件）      | 两次解读结论一致数 ÷ 总样本数     | 47/50一致 → 94分    |
| 处置结论稳定性（漏洞）         | 两次"是否立即处置"一致数 ÷ 总样本数 | 43.5/50一致 → 87分  |
| 重复执行稳定性（检测类）        | N次执行结论一致数 ÷ 总样本数     | 98/100一致 → 98分   |
| 执行成功率 VER（text2sql） | 全步骤成功题数 ÷ 总题数        | 392/400成功 → 98分  |
| 稳定性成功率（WAF/情报）      | 成功请求数 ÷ 总请求数         | 600/600成功 → 100分 |

> 说明：这类指标的特点是"每次测试只有通过/不通过两种结果"，多样本时统计通过率。LLM Judge类稳定性指标（告警/事件）也归入此类，因为最终结论是"一致/不一致"的二元判断。

#### 类型4：score\_based（已有评分）

**公式**：`标准分 = raw_score ÷ max_score × 100`

**含义**：原始数据已经是打分制（如100分制），直接按比例转为0\~100标准分。无需额外归一化，只需声明满分值。

**适用指标**：

| 指标            | max\_score | 示例                     |
| ------------- | ---------- | ---------------------- |
| 整体内容合规性（告警审查） | 100        | 92分 → 92÷100×100 = 92分 |
| 整体内容合规性（事件审查） | 100        | 91分 → 91分              |
| 整体内容合规性（资产审查） | 100        | 81分 → 81分              |
| 整体内容合规性（漏洞审查） | 100        | 92分 → 92分              |
| 处置建议合理性（沙箱）   | 100        | 72.7分 → 72.7分          |
| 整体内容正确性（检测类）  | 100        | 92% → 92分              |
| 报告内容准确性（数字人）  | 100        | 70% → 70分              |

> 说明：LLM Judge类指标均归入此类。关键设计：LLM只负责识别违规规则ID，分数由程序（score\_calculator.py）精确计算，禁止LLM自行算分，保证评分可重复、可审计。

#### 完整算分流程（评分引擎内部分层计算）

评分引擎（`core/scoring_engine.py`）内部也采用分层设计，从下往上四层，每层职责独立：

```
第四层：整体综合分    类内均值 → 类间等权 → 整体分+评级
第三层：智能体综合分  维度分按分类权重加权 → 综合分
第二层：维度归并      同维度内标准分取均值 → 维度分
第一层：指标归一化    原始值 → 0~100标准分
```

每层只依赖下一层的输出，修改某一层不影响其他层（如改权重不影响归一化公式，改归一化公式不影响维度归并）。所有算分逻辑已固化在代码中，评审通过后由代码自动计算，不手动填数。

**第一层：指标归一化（原始值 → 0\~100标准分）**

按上述四种归一化类型，每个指标转为0\~100标准分。示例：

```
WAF F1=0.977 → higher_better(best=1.0) → 97.7分
告警首包=0.2s → lower_better(best=0.5s, worst=5.0s) → 100分（截断）
告警内容合规=92分 → score_based(max=100) → 92分
告警核心结论稳定性=47/50 → pass_fail → 94分
```

> 为什么需要这一层：13个智能体的指标量纲完全不同——准确率是0\~1、F1是0\~1、响应时间是秒、LLM审查是100分制，无法直接比较或加权。归一化到统一的0\~100标准分后，才能在同一维度内合并、跨维度加权。

**第二层：维度归并（同维度内标准分取均值 → 维度分）**

```
告警解读准确性维度 = mean(威胁定性100分, 攻击结果98分) = 99分
告警解读性能维度 = mean(首包100分, 平均响应91.7分) = 95.9分
告警解读内容质量维度 = mean(格式合规98分, 内容合规92分) = 95分
告警解读可靠性维度 = 核心结论稳定性94分 = 94分
```

> 为什么用均值而不是加权：同一维度内的子指标业务重要性相当（如威胁定性和攻击结果同等重要），没有充分理由给不同权重。如果某个子指标特别重要，应单独拆成一个维度而不是在维度内加权，保持维度内均值简单透明。

**第三层：智能体综合分（维度分按分类权重加权 → 综合分）**

权重按智能体分类决定。缺失维度排除，分母调整。

```
告警解读（内容生成类：准35% 靠20% 内35% 性10%）
= (99×35 + 94×20 + 95×35 + 95.9×10) ÷ (35+20+35+10)
= (3465 + 1880 + 3325 + 959) ÷ 100
= 96.3分 → S级

资产解读（内容生成类，无可靠性维度）
= (100×35 + 89.5×35 + 88.7×10) ÷ (35+35+10)    ← 排除可靠性20%
= (3500 + 3132.5 + 887) ÷ 80
= 94.0分 → S级
```

> 为什么按分类加权而不是四维等权：不同类型智能体的业务重点不同——检测类核心是"判断对不对"（准确性权重50%），生成类核心是"报告写得好不好"（内容质量权重35%），用同一套权重会让检测类被内容质量拉低分、生成类被准确性拉低分，不公平。分类加权让每类智能体按自己的业务重点评分。
>
> 为什么缺失维度排除而不是给默认分：给默认分（如80分）会人为拉高或拉低综合分，不反映真实水平。排除缺失维度、调整分母，保证只基于已有数据计算，结果更客观。

**第四层：整体综合分（类内均值 → 类间等权 → 整体分）**

```
第一步：类内均值
  检测类 = mean(WAF 97.6, Webshell 95.5, 恶意文件 90.9, 钓鱼 83.0, 情报 94.5) = 92.3
  生成类 = mean(告警 96.3, 事件 96.3, 资产 94.0, 漏洞 87.7, 沙箱 90.1) = 92.9
  查询类 = mean(text2sql 85.4, 数字人 82.0) = 83.7
  问答类 = RAG 80.5

第二步：类间等权均值（4类话语权相等，不按智能体数量加权）
  整体综合分 = mean(92.3, 92.9, 83.7, 80.5) = 87.3分 → A级
```

> 为什么类间等权而不是按智能体数量加权：检测类5个智能体、查询类2个、问答类1个。如果按数量加权，检测类话语权是问答类的5倍，整体分会被检测类主导，不能反映平台全面水平。类间等权让每类对整体分的贡献相等，更公平。
>
> 为什么不直接对13个智能体取均值：13个智能体取均值会让数量多的类别主导整体分（检测类5个占5/13=38%话语权），数量少的类别被淹没（问答类1个占1/13=8%）。类间等权避免了这个问题。

#### 算法合理性总结

| 设计决策   | 选择了什么         | 为什么这样选        | 替代方案的缺陷        |
| ------ | ------------- | ------------- | -------------- |
| 指标归一化  | 四种类型统一到0\~100 | 量纲不同无法直接比较    | 不归一化则无法跨指标加权   |
| 维度内合并  | 简单均值          | 子指标重要性相当，保持透明 | 加权会增加主观性，无充分依据 |
| 跨维度加权  | 按分类配权重        | 不同业务重点不同，需差异化 | 等权会让检测类被内容质量拉低 |
| 缺失维度处理 | 排除+调整分母       | 只基于已有数据计算     | 给默认分会人为拉高/拉低   |
| 整体综合分  | 类间等权          | 避免数量多的类别主导    | 按数量加权不公平       |
| 评级     | 短板锁定+红线       | 防止高分维度掩盖短板    | 纯加权均值会掩盖短板     |
| 版本判定   | 逐指标对比+门禁      | 发布决策看退化不看总分   | 综合分会掩盖个别指标退化   |

分类权重（按业务重要性配置，评审后修订。性能不算分，权重分配到其他维度）：

| 类别    | 准确性 | 可靠性 | 内容质量 |  性能 | 权重设计依据     |
| ----- | :-: | :-: | :--: | :-: | ---------- |
| 检测研判类 | 90% |  5% |  5%  | 不算分 | 核心职责是判断对不对 |
| 内容生成类 | 70% | 15% |  15% | 不算分 | 核心价值是报告质量  |
| 查询类   | 80% | 10% |  10% | 不算分 | 核心是结果正确    |
| 知识问答类 | 90% |  5% |   5% | 不算分 | 答案质量很重要    |

评级标准（短板锁定 + 红线）：

| 评级 | 条件                 | 对外表述        |
| -- | ------------------ | ----------- |
| S  | 综合分 ≥90 且 所有维度 ≥85 | 生产就绪，建议全量使用 |
| A  | 综合分 ≥80 且 所有维度 ≥70 | 生产可用，关注短板   |
| B  | 综合分 ≥70 且 所有维度 ≥60 | 受限使用，限定场景   |
| C  | 综合分 ≥60            | 建议不上线，优化后复测 |
| D  | 综合分 <60 或 任意维度 <60 | 禁止上线        |

缺失维度处理：自动排除，分母相应调整。

### 3.3 四个测试维度

所有智能体的指标归入四个维度：

| 维度   | 核心问题           | 典型指标                     |
| ---- | -------------- | ------------------------ |
| 准确性  | AI结论与事实真值是否一致  | 判定准确率、F1、威胁定性准确率、风险等级准确率 |
| 可靠性  | 同输入多次执行结论是否一致  | 核心结论稳定性、重复执行稳定性          |
| 内容质量 | 报告是否规范、有逻辑、可执行 | 格式合规率、LLM审查评分、处置建议合理性    |
| 性能   | 响应速度是否达标       | 首包响应时间、平均响应时间、P95/P99    |

**不是每个智能体都要测全部维度**，允许空缺（报告中显示"—"）。

### 3.4 指标归一化配置

每个智能体声明自己的指标、所属维度、归一化类型、阈值和**必填字段**。新智能体接入只需写一个声明文件：

```yaml
# 示例：安全告警解读智能体声明
agent:
  id: ai_interpret_alarm
  name: 安全告警解读
  category: generate          # 决定权重

metrics:
  - key: threat_determination_accuracy
    dimension: accuracy
    type: higher_better
    thresholds: {best: 1.0, worst: 0.0}
    required_fields: [accuracy]          # ← 这个指标必填accuracy字段
    is_guardrail: true
    regression_threshold: 0.05

  - key: first_packet_time
    dimension: performance
    type: lower_better
    thresholds: {best: 0.5, worst: 5.0}
    required_fields: [value]            # ← 这个指标必填value字段
    is_guardrail: false
    regression_threshold: 0.20

  - key: content_compliance
    dimension: content_quality
    type: score_based
    thresholds: {max_score: 100}
    required_fields: [accuracy]          # ← LLM审查分转化为0~1
    is_guardrail: false
```

#### required\_fields 声明规则

每个指标声明 `required_fields`，告诉接收端该指标必须填哪些字段。按归一化类型对应：

| 归一化类型          | required\_fields | 说明                      |
| -------------- | :--------------: | ----------------------- |
| higher\_better |   `[accuracy]`   | 引擎用 accuracy×100 计算标准分  |
| pass\_fail     |   `[accuracy]`   | 引擎用 accuracy×100 计算标准分  |
| score\_based   |   `[accuracy]`   | LLM审查分转化为0\~1后填accuracy |
| lower\_better  |     `[value]`    | 引擎按best/worst阈值归一化      |

#### 接收端校验逻辑

接收端收到上传后，按该智能体的声明文件逐条校验：

```
1. 按 agent_id 找到声明文件（config/agents/{agent_id}.yaml）
2. 逐条校验：
   a. 每条数据的 metrics 是否和声明一致
   b. 每个指标的 required_fields 是否都填了 → 缺失则拒绝
   c. 声明里没有的指标 → 拒绝（防止误插入其他智能体的字段）
   d. 声明里有的指标但数据里没填 → 拒绝
   e. 声明外的额外字段 → 忽略
3. 校验通过 → 存储
4. 校验失败 → 返回具体错误信息
```

#### 两个智能体的声明对比

```yaml
# 告警解读：需要填accuracy的指标多
metrics:
  - key: threat_determination_accuracy
    required_fields: [accuracy]       # 威胁定性准确率
  - key: first_packet_time
    required_fields: [value]           # 首包响应时间
  - key: content_compliance
    required_fields: [accuracy]         # LLM审查分

# WAF降噪：指标少，字段简单
metrics:
  - key: f1_score
    required_fields: [accuracy]         # F1值
  - key: avg_response_time
    required_fields: [value]            # 平均响应时间
  - key: stability_rate
    required_fields: [accuracy]         # 稳定性成功率
```

每个智能体声明不同，接收端按各自声明校验，不会出现WAF的数据里混入告警特有的字段。

### 3.5 版本判定报告样例

```

综合得分：86 → 91（↑5分，评级 A→S）

  · 所有门禁指标退化均未超阈值

```

## 四、团队协作机制

### 4.1 角色分工

| 角色            | 职责               | 产出                |
| ------------- | ---------------- | ----------------- |
| **各智能体测试负责人** | 跑测试，输出标准格式结果     | `{agent_id}.json` |
| **框架汇总人**     | 收集JSON，归一化打分，出报告 | 综合报告HTML          |
| **版本评审人**     | 看报告，确认门禁，决定是否发布  | 发布决策              |

### 4.2 各智能体测试负责人需要做什么

**只做一件事**：跑完测试后，把结果转成 `StandardResult` JSON数组，通过HTTP接口上传。

#### 上传接口

```
POST /api/v1/results?agent_id={agent_id}&run_id={run_id}
Content-Type: application/json

请求参数（query）:
  agent_id:  智能体标识（必填）
  run_id:    批次标识（必填），如 v190_20261117

请求体:
  StandardResult JSON数组（每条数据无需再填agent_id和run_id，接收端自动补）

响应:
  200 {"status": "ok", "agent_id": "waf_dedup", "run_id": "v190_20261117", "count": 600, "saved_to": "results/v190_20261117/waf_dedup.json"}
  400 {"status": "error", "message": "字段校验失败: sample_id必填"}
  500 {"status": "error", "message": "服务器内部错误"}
```

#### 上传示例

**方式1：curl命令行上传**

```bash
curl -X POST "http://10.x.x.x:8080/api/v1/results?agent_id=waf_dedup&run_id=v190_20261117" \
  -H "Content-Type: application/json" \
  -d @waf_dedup_results.json
```

**方式2：Python requests上传**

```python
import requests

results = [
    {"sample_id": "attack_001", "case_id": "waf_test_01", "status": "valid", "metrics": [...]},
    {"sample_id": "attack_002", "case_id": "waf_test_02", "status": "valid", "metrics": [...]},
]

resp = requests.post(
    "http://10.x.x.x:8080/api/v1/results",
    params={"agent_id": "waf_dedup", "run_id": "v190_20261117"},
    json=results
)
print(resp.json())
# → {"status": "ok", "agent_id": "waf_dedup", "run_id": "v190_20261117", "count": 600, "saved_to": "results/v190_20261117/waf_dedup.json"}
```

> requests是Python标准库自带，各团队无需安装额外依赖。
> agent\_id和run\_id在URL中传入，每条数据无需重复填写，接收端自动补入。

#### 接收端处理流程

```
1. 接收POST请求，校验JSON格式和必填字段
2. 按agent_id存入 results/{run_id}/{agent_id}.json
3. 返回上传结果（条数、存储路径）
4. 框架汇总引擎扫描目录，自动读取所有JSON → 归一化打分 → 出报告
```

#### 批量上传

如果样本量大（如恶意文件1200条），建议分批上传，每批不超过500条：

```bash
# 分批上传
curl -X POST "http://10.x.x.x:8080/api/v1/results?agent_id=malfile_detect&run_id=v190_20261117&batch=1" \
  -H "Content-Type: application/json" \
  -d @malfile_batch1.json    # 前500条

curl -X POST "http://10.x.x.x:8080/api/v1/results?agent_id=malfile_detect&run_id=v190_20261117&batch=2" \
  -H "Content-Type: application/json" \
  -d @malfile_batch2.json    # 后500条
```

接收端自动合并同一agent\_id的多批次数据。

#### 接收端存储

接收端收到上传后，按agent\_id存入目录：

```
outputs/results/{run_id}/
├── waf_dedup.json              ← WAF团队上传
├── malfile_detect.json         ← 恶意文件团队上传
├── webshell_detect.json
├── phishing_detect.json
├── ioc_extract.json
├── ai_interpret_alarm.json
├── ai_interpret_event.json
├── ai_interpret_asset.json
├── ai_interpret_vuln.json
└── ai_interpret_sandbox.json
```

#### 文件组织规则

- **一个文件 = 一个智能体的所有样本**，文件名即 `agent_id`
- **一条 StandardResult = 一个样本**（如一个告警ID、一个文件样本）
- 一个JSON文件是一个数组，包含该智能体的所有样本结果

#### raw\_text 处理策略

StandardResult JSON **不保留 raw\_text（AI原始报告全文）**，原因：

| 场景      | 是否需要raw\_text | 理由         |
| ------- | :-----------: | ---------- |
| 统一汇总报告  |     ❌ 不需要     | 报告只需指标数据   |
| 版本对比报告  |     ❌ 不需要     | 只比指标变化     |
| 下钻看样本详情 |     ❌ 不需要     | 指标数据够用     |
| 归档存档    |      ✅ 需要     | 单独存，不进JSON |

原文单独存在各智能体自己的输出目录（如 `outputs/ai_test_agent/{run_id}/alarm_raw_md/`）。框架需要展示原文时，按 `sample_id` 去原目录查找。

#### 文件大小估算

| 智能体      |   样本数   | 不含raw\_text | 含raw\_text |
| -------- | :-----: | :---------: | :--------: |
| 告警解读     |   50条   |   \~30 KB   |  \~200 KB  |
| 恶意文件检测   |  1200条  |   \~500 KB  |   \~4 MB   |
| WAF降噪    |   600条  |   \~250 KB  |   \~2 MB   |
| 全部13个智能体 | \~8000条 |    \~3 MB   |   \~20 MB  |

不含raw\_text时，全部13个智能体总计约3MB，传输和处理都很快。

### 4.4 各字段说明

| 字段                    | 类型     |    必填    | 说明                                                                                                                                                                                                           |
| --------------------- | ------ | :------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `agent_id`            | string |   URL传入  | 智能体唯一标识，通过URL query参数传入，接收端自动补入每条数据                                                                                                                                                                          |
| `run_id`              | string |   URL传入  | 批次标识，通过URL query参数传入，接收端自动补入每条数据                                                                                                                                                                             |
| `case_id`             | string |     ✅    | 测试用例编号，如 `alarm_test_01`                                                                                                                                                                                     |
| `sample_id`           | string |     ✅    | 业务样本ID，如告警ID                                                                                                                                                                                                 |
| `status`              | string |     ✅    | `valid` / `failed` / `invalid`                                                                                                                                                                               |
| `first_packet_time`   | float  |          | 首包响应时间（秒），有则填                                                                                                                                                                                                |
| `total_response_time` | float  |          | 总响应时间（秒），有则填                                                                                                                                                                                                 |
| `metrics`             | array  |     ✅    | 指标列表，每条含维度标签                                                                                                                                                                                                 |
| `metrics[].dimension` | string |     ✅    | 维度标签：`accuracy`（准确性）/ `reliability`（可靠性）/ `content_quality`（内容质量）/ `performance`（性能）                                                                                                                         |
| `metrics[].key`       | string |     ✅    | 指标标识，如 `threat_determination_accuracy`（威胁定性准确率）                                                                                                                                                              |
| `metrics[].name_cn`   | string |     ✅    | 中文名，如"威胁定性准确率"                                                                                                                                                                                               |
| `metrics[].value`     | any    | **条件必填** | AI输出值（被测智能体给出的结果）。**performance维度必填**（原始时间值，如0.2秒）；**content\_quality维度的score\_based类型必填**（原始分数，如92分）。示例：威胁定性AI判定为"正报"则value="正报"；首包时间0.2秒则value=0.2                                                         |
| `metrics[].expected`  | any    |          | 基准真值（标准答案/API返回的真实值）。示例：威胁定性API返回"正报"则expected="正报"；首包时间期望≤3秒则expected="≤3s"。用于人工核对AI值和真值是否一致，不参与自动计分                                                                                                        |
| `metrics[].accuracy`  | float  | **条件必填** | 该指标AI答对的程度，取值0\~1。**accuracy/reliability/content\_quality维度必填**。1.0=完全正确，0.0=完全错误，0.94=94%通过率。示例：AI判定"正报"且API也是"正报"→accuracy=1.0；50个样本47个结论一致→accuracy=0.94。引擎用 accuracy×100 计算标准分。performance维度不填（填null或不填） |
| `metrics[].passed`    | bool   |     ✅    | 该指标是否通过                                                                                                                                                                                                      |
| `metrics[].detail`    | object |          | 明细信息                                                                                                                                                                                                         |
| `raw_text`            | string |          | AI原始输出（**置空，不传输全文**，原文存各智能体输出目录）                                                                                                                                                                             |
| `error`               | string |          | 失败/失效原因                                                                                                                                                                                                      |
| `timestamp`           | string |          | 结果生成时间                                                                                                                                                                                                       |

#### 必填字段与归一化类型的对应关系

| 归一化类型          | 必填字段             | 示例                  | 说明                             |
| -------------- | ---------------- | ------------------- | ------------------------------ |
| higher\_better | `accuracy`（0\~1） | `"accuracy": 0.977` | 引擎用 accuracy×100 计算标准分         |
| pass\_fail     | `accuracy`（0\~1） | `"accuracy": 0.94`  | 引擎用 accuracy×100 计算标准分         |
| score\_based   | `value`（原始分数）    | `"value": 92`       | 引擎用 value÷max\_score×100 计算标准分 |
| lower\_better  | `value`（原始时间值）   | `"value": 0.2`      | 引擎按best/worst阈值归一化计算标准分        |

> 简记：accuracy/reliability/content\_quality 维度的指标填 `accuracy`，performance 维度的指标填 `value`。

### 4.5 各智能体需要提供的指标映射

每个智能体测试负责人对照下表，确认自己输出的指标归入哪个维度：

**检测研判类：**

| 智能体        | 准确性              | 可靠性    | 内容质量          | 性能           |
| ---------- | ---------------- | ------ | ------------- | ------------ |
| WAF降噪      | 判定准确率、F1(P/R)    | 稳定性成功率 | 整体内容正确性       | 平均响应、P95/P99 |
| 恶意文件检测     | 判定准确率、F1         | 稳定性    | 格式合规率、整体内容正确性 | 首包、平均响应      |
| Webshell检测 | 整体准确率、F1、威胁等级准确率 | 重复稳定性  | 格式合规率、整体内容正确性 | 首包、平均响应      |
| 钓鱼邮件检测     | 判定准确率、F1         | 重复稳定性  | 格式合规率、整体内容正确性 | 首包、平均响应      |
| 本地情报提取     | IOC召回率、精确率、F1    | 稳定性成功率 | 整体内容正确性       | 平均响应         |

### 4.6 协作流程

```
版本测试周期（如 v190 发布前）

Step 1: 确认本次参测智能体和指标清单（QA团队组织）
    ↓
Step 2: 各测试负责人跑测试，输出 StandardResult JSON
    → 通过HTTP接口上传到接收端
    → POST /api/v1/results?agent_id={agent_id}
    → 接收端校验后存入 outputs/results/{run_id}/{agent_id}.json
    ↓
Step 3: 框架汇总人执行汇总脚本
    → python run_unified_report.py --run-id v190_20261117
    → 扫描目录读取所有JSON → 归一化 → 打分 → 对比 → 出报告
    ↓
Step 4: 版本评审会
    → 看报告，确认门禁，决定是否发布
    → 各测试负责人确认退化项是否可接受
    ↓
Step 5: 归档
    → 报告存入 outputs/reports/{run_id}/
    → 作为版本基线，供下一期对比
```

### 4.7 新智能体接入流程

```
新智能体接入只需3步：

Step 1: 确认分类（检测研判/内容生成/查询/知识问答）
    → 决定权重配置

Step 2: 编写指标声明文件
    → 声明每个指标的维度归属、归一化类型、阈值
    → 放到 config/agents/{agent_id}.yaml

Step 3: 测试脚本输出 StandardResult JSON
    → 跑完测试后转成标准格式
    → 通过HTTP接口上传: POST /api/v1/results?agent_id={agent_id}
    → 接收端自动存入 outputs/results/{run_id}/{agent_id}.json

框架自动发现 → 自动打分 → 自动进报告
```

## 六、风险与应对

| 风险                       | 应对                                              |
| ------------------------ | ----------------------------------------------- |
| 各团队适配StandardResult格式有成本 | 提供JSON模板 + 13个示例 + 适配指南，curl/requests上传，无需安装SDK |
| 权重配置主观性                  | 先定初始值，写明依据，后续根据实际退化分布调整                         |
| 归一化阈值需按智能体配置             | 声明式配置，每个智能体独立设定阈值                               |
| 跨版本缺维度导致对比不公平            | 版本对比时取两期共同维度做对比，不比单期综合分                         |
| LLM Judge结果有波动           | 多次取均值，或固定种子；门禁阈值留足余量                            |

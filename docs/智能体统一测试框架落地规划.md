> 文档版本：v1.0
> 编写时间：2026-11-10
> 负责团队：AIXDR QA 团队

## 一、背景与目标

### 1.1 现状问题

当前 AIXDR AI 测试体系围绕"解读类智能体"构建，存在以下结构性问题：

| 问题 | 表现 | 影响 |
|------|------|------|
| **单智能体强耦合** | `MODULE_CONFIG` 硬编码 5 个模块，指标计算逻辑写死在 `AIInterpretAgent._calculate_metrics()` 的 300 行 if-elif 中 | 接入新智能体必须改核心代码，无法扩展 |
| **结果无身份标识** | `TestResult` 没有 `agent_id` 字段，无法区分结果来自哪个智能体 | 报告无法做跨智能体横向对比 |
| **指标无维度归类** | 计算器没有维度标签，所有指标混在一起算 | 无法支持"只跑准确性""只跑稳定性"的按需裁剪 |
| **接入方式单一** | 只有框架主动调 AI 接口一种模式 | 其他团队的智能体无法接入 |

### 1.2 目标

构建一个**智能体统一测试框架**，实现：

1. **统一接入**：所有智能体的测试结果汇入同一框架，支持两种接入模式
2. **统一报告**：第一张表呈现各智能体准确性数据，支持横向对比
3. **按需裁剪**：支持只跑准确性维度、只跑某个智能体、或组合筛选
4. **低门槛扩展**：新智能体接入 = 加一段配置，零代码改动

### 1.3 约束

- **不推倒重来**：现有 calculators、extractors、api_clients、reporter 全部复用
- **向后兼容**：重构期间现有定时任务（解读测试/审查/稳定性）不中断
- **渐进式迁移**：分三步演进，每步可独立验证、独立上线

## 二、目标架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                   统一测试报告门户 (HTML)                       │
│                                                              │
│  Table1:准确性   Table2:性能   Table3:稳定性   Table4:合规审查  │
│  每张表横向排列各智能体，支持点击下钻到单智能体明细              │
└───────────────────────────▲──────────────────────────────────┘
                            │ StandardResult（标准结果契约）
┌───────────────────────────┴──────────────────────────────────┐
│                    测试调度内核 (Orchestrator)                  │
│                                                              │
│  读 manifest → 按 --agent / --dimension 过滤 → 调度执行        │
│  支持: run --all / --agent=X / --dimension=accuracy / 组合     │
└──────────┬───────────────────────────────────┬───────────────┘
           │ Pull 模式                          │ Push 模式
┌──────────┴──────────────────┐     ┌──────────┴──────────────────┐
│ PullAdapter（主动调用）      │     │ 接收端（被动接收）            │
│                             │     │                             │
│ 调 AI 接口 → 解析 → 算指标   │     │ HTTP 接收 StandardResult     │
│ → 产出 StandardResult       │     │ → 入库 → 供报告聚合           │
│                             │     │                             │
│ （现有代码归入此层）         │     │ （其他团队按契约 POST 结果）   │
└─────────────────────────────┘     └─────────────────────────────┘
```

### 架构分层说明

| 层次 | 职责 | 改动情况 |
|------|------|---------|
| **报告门户** | 按维度横向对比各智能体，支持下钻 | 改造现有 HTMLReportGenerator |
| **调度内核** | 读配置、按筛选条件调度执行、聚合结果 | 新建，从 AIInterpretAgent 中拆出 |
| **PullAdapter** | 主动调 AI 接口、解析输出、计算指标 | 现有代码搬迁，零逻辑改动 |
| **Push接收端** | 接收外部团队提交的标准结果 | 新建，轻量 HTTP 服务 |
| **契约层** | StandardResult 数据结构 + 维度定义 | 新建，贯穿所有层 |

## 三、核心概念定义

### 3.1 StandardResult — 标准结果契约

所有智能体的测试结果，无论 Pull 还是 Push，最终都归一为 `StandardResult` 结构。这是整个框架的地基，也是提供给其他同事的"规定返回结构"。

```python
@dataclass
class StandardResult:
    # ── 身份标识 ──
    agent_id: str            # 智能体唯一标识，如 "ai_interpret_alarm"
    case_id: str             # 测试用例编号，如 "alarm_test_01"
    sample_id: str           # 业务样本ID，如 "7927904014451048448"
    run_id: str              # 本次批次ID（时间戳），用于聚合归档

    # ── 样本分类（与现有体系一致）──
    status: str              # "valid" / "failed" / "invalid"

    # ── 响应性能（Pull模式有值，Push模式可选）──
    first_packet_time: float  # 首包响应时间（秒）
    total_response_time: float # 总响应时间（秒）

    # ── 维度化指标列表 ──
    metrics: list[Metric]    # 每个指标都带 dimension 标签

    # ── 溯源 ──
    raw_text: str            # AI原始输出（Pull模式有值）
    error: str               # 失败/失效原因
    timestamp: str           # 结果生成时间


@dataclass
class Metric:
    dimension: str           # "accuracy" / "performance" / "stability" / "compliance"
    key: str                 # "threat_determination_accuracy"
    name_cn: str             # "威胁定性准确率"
    value: Any               # AI解读值
    expected: Any            # 基准真值
    accuracy: float | None   # 0~1，None=提取失败（不计入均值）
    passed: bool             # 是否通过
    detail: dict             # 明细（缺失章节、扣分项等）
```

### 3.2 维度标签体系

将现有所有指标归入四个维度，使"只跑准确性"成为可能：

| 维度 | 英文标识 | 包含的指标（现有） | 说明 |
|------|---------|------------------|------|
| **准确性** | `accuracy` | 风险等级准确率、威胁定性准确率、攻击结果准确率、结构完整率、动态结构完整率、样本信息提取 | 核心维度，报告第一张表 |
| **性能** | `performance` | 首包响应时间、总响应时长 | 响应速度 |
| **稳定性** | `stability` | 核心结论稳定性（双次对比） | 结论一致性 |
| **合规审查** | `compliance` | LLM审查评分（31~40条规则）、推荐问题质量 | 规范符合度 |

> **注**：沙箱模块的"处置建议合理性"归入 `accuracy`（因为衡量的是结论正确性）；"格式规范性""章节完整性"归入 `compliance`。

### 3.3 Agent Manifest — 智能体清单

用声明式 YAML 配置替代现在硬编码的 `MODULE_CONFIG`：


## 四、实施步骤

### 第一步：抽契约层 + 维度标签（地基）

**目标**：定义标准结果契约，给现有指标打上维度标签，使结果数据具备跨智能体聚合的能力。

**改动范围**：

| 文件 | 改动内容 | 风险 |
|------|---------|------|
| 新建 `core/contract.py` | 定义 `StandardResult`、`Metric` 数据类 | 无（纯新增） |
| `core/calculators/base_calculator.py` | `BaseCalculator` 增加 `DIMENSION` 类属性 | 低（加字段，不改逻辑） |
| 各 calculator 文件（9个） | 每个计算器类加一行 `DIMENSION = "accuracy"` 等 | 低（加一行） |
| `agents/ai_interpret_agent.py` | `TestResult` 增加 `agent_id` 字段；`run_test_case()` 结尾将结果转换为 `StandardResult` | 低（加转换层，原有逻辑不动） |

**具体改动清单**：

```
1. 新建 core/contract.py
   - StandardResult dataclass
   - Metric dataclass
   - DIMENSION 枚举常量

2. core/calculators/base_calculator.py
   - BaseCalculator 增加: DIMENSION = ""
   - MetricResult.to_dict() 输出中增加 "dimension" 字段

3. 给每个 calculator 打标签:
   - risk_level_calc.py          → DIMENSION = "accuracy"
   - threat_determination_calc.py → DIMENSION = "accuracy"
   - attack_result_calc.py       → DIMENSION = "accuracy"
   - structure_completeness_calc.py → DIMENSION = "accuracy"
   - dynamic_structure_completeness_calc.py → DIMENSION = "accuracy"
   - response_time_calc.py       → DIMENSION = "performance"
   - field_completeness_calc.py  → DIMENSION = "accuracy"
   - format_compliance_calc.py   → DIMENSION = "compliance"
   - cvss_calc.py                → DIMENSION = "accuracy"
   - recommend_question_calc.py  → DIMENSION = "compliance"
   - sandbox_calculators.py      → 各子类分别打标签

4. agents/ai_interpret_agent.py
   - TestResult 增加 agent_id 字段（默认值取 MODULE_CONFIG）
   - 新增 to_standard_result() 转换方法
   - run_test_case() 结尾调用 to_standard_result()，不改原有流程
```

**产出**：
- `core/contract.py` — 标准结果契约定义
- 所有 calculator 带维度标签
- 现有测试流程产出的结果可转换为 `StandardResult`

**验证方式**：
- 运行 `python run_ai_test_agent.py --module alarm`，确认结果正常产出
- 确认产出的 `StandardResult` JSON 包含 `agent_id` 和每个 metric 的 `dimension` 字段
- 确认现有 HTML 报告不受影响

**预计工期**：1.5 天

### 第二步：抽调度内核 + Manifest 配置化

**目标**：将调度逻辑从 `AIInterpretAgent` 中拆出，用 manifest 配置驱动执行，支持按智能体/维度裁剪。

**改动范围**：

| 文件 | 改动内容 | 风险 |
|------|---------|------|
| 新建 `config/agents_manifest.yaml` | 所有智能体的声明式配置 | 无（纯新增） |
| 新建 `core/orchestrator.py` | 调度内核：读配置、按筛选过滤、调度执行、聚合结果 | 中（新核心模块） |
| 新建 `core/pull_adapter.py` | 从 `AIInterpretAgent` 拆出的主动调用逻辑 | 中（代码搬迁+解耦） |
| 改造 `run_ai_test_agent.py` | 入口改为调用 Orchestrator，支持 `--agent`/`--dimension` 参数 | 低（入口层） |
| `AIInterpretAgent` | 降级为 PullAdapter 的内部实现，保留向后兼容 | 低 |

**新的执行命令**：

```bash
# 全量执行（等价于现有 --mode all）
python run.py --all

# 只跑某个智能体
python run.py --agent ai_interpret_alarm

# 只跑准确性维度（所有智能体）
python run.py --dimension accuracy

# 组合：只跑告警智能体的准确性
python run.py --agent ai_interpret_alarm --dimension accuracy

# 多智能体
python run.py --agent ai_interpret_alarm,ai_interpret_event
```

**调度内核工作流程**：

```
1. 加载 agents_manifest.yaml
2. 按 --agent / --dimension 过滤出命中的 (agent, dimension) 组合
3. 对每个命中的 agent:
   a. Pull 模式 → 调 PullAdapter 执行（调API→解析→只跑命中的calculators）
   b. Push 模式 → 跳过执行（等接收端收数据）
4. 收集所有 StandardResult
5. 按 dimension 聚合 → 传给报告生成器
```

**产出**：
- `config/agents_manifest.yaml` — 智能体清单配置
- `core/orchestrator.py` — 调度内核
- `core/pull_adapter.py` — 主动调用适配器
- 改造后的入口脚本，支持按维度/智能体裁剪

**验证方式**：
- `python run.py --agent ai_interpret_alarm --dimension accuracy` 只跑告警的准确性指标，性能指标不执行
- `python run.py --dimension accuracy` 所有智能体只跑准确性
- `python run.py --all` 全量执行，结果与重构前一致
- 现有定时任务脚本无需修改（入口保持兼容）

**预计工期**：2.5 天

## 五、团队配合准备

### 5.1 接入模式选择

其他团队的智能体接入时，根据能否直接调用 AI 接口，选择一种模式：

| | Pull 模式 | Push 模式 |
|---|---|---|
| **前提条件** | 我们能直接调到该智能体的接口 | 该团队有自己的测试链路 |
| **对方需要做什么** | 提供接口信息、测试数据、指标定义 | 按契约实现适配器，提交 StandardResult |
| **我方需要做什么** | 在 manifest 加一段配置 | 提供契约文档 + SDK + 接收端地址 |
| **适用场景** | 解读类智能体（现状） | 其他团队独立开发的智能体 |

### 5.2 Pull 模式接入 — 对方需要提供的信息

其他团队如果选择 Pull 模式（我们主动调他们的智能体），需要提供：

```
□ 智能体标识（id）和中文名称
□ 接口地址和协议（SSE / HTTP JSON / 异步轮询）
□ 请求参数结构（bizType、agent 参数等）
□ 测试样本数据（ID列表或数据集）
□ 该智能体适用的评测指标（从现有指标中选，或定义新指标）
□ 终止信号说明（什么标志表示报告生成完成）
□ 鉴权方式（如有）
```

提供后，我们在 `agents_manifest.yaml` 加一段配置即可，无需对方改代码。

### 5.3 Push 模式接入 — 对方需要做的事

其他团队如果选择 Push 模式（自己跑测试，推结果给我们），需要完成以下步骤：

```
Step 1: 阅读接入文档
  → docs/StandardResult契约说明.md（第三步产出后提供）

Step 2: 安装 SDK（或自行实现 HTTP 提交）
  → pip install aixdr-test-sdk（或直接 POST JSON）

Step 3: 编写适配器
  → 将你们智能体的测试结果，转换为 StandardResult 结构
  → 关键字段: agent_id / sample_id / status / metrics(带dimension标签)
  → 参考 SDK 中的示例代码

Step 4: 对接联调
  → 向接收端 POST 一条测试数据，确认返回 200
  → 确认数据出现在统一报告中

Step 5: 接入定时任务
  → 你们的测试脚本跑完后，自动调用 SDK 提交结果
  → 或约定一个 run_id，批量提交
```

**Push 模式适配器示例（给其他同事参考）**：

```python
from aixdr_test_sdk import StandardResult, Metric, submit_result

# 你们智能体跑完测试后，构造结果提交
result = StandardResult(
    agent_id="xdr_copilot",
    case_id="copilot_test_01",
    sample_id="query_001",
```

## 七、风险与应对

| 风险 | 概率 | 影响 | 应对 |
